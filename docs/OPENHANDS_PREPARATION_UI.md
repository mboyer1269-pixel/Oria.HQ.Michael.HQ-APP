# OpenHands mission dossier UI (server feature remains off)

The existing mission dossier now contains a compact collapsible OpenHands preparation section. Its enabled prop comes only from the existing server process flag ORIA_ENABLE_OPENHANDS_CONFIRMATION; no environment setting is changed. Flag off or non-durable mission shows an explanatory label and no submission controls. No redesign, provider launch or deployment.

Owner supplies an explicit full commit, executor version and desired budget values. No version or spending amount is preselected. Prepare validates the server response against mission/workspace/version/commit/version/budgets and refuses unknown dossier fields. The snapshot is frozen. The review displays objective, scope, acceptance criteria, expected result, each requested limit, commit/version and the exhaustive JSON identity/hash. All text is React-escaped.

The warning is explicit: reservation only, no agent launch; repository commit and installed version are not verified; cost/tokens/duration limits are requested values, not guaranteed enforced caps; OpenHands iterations do not equal model turns. Confirmation requires a fresh explicit checkbox and submits the displayed payload hash with the frozen request parameters.

An immediate in-flight ref blocks double clicks in the mounted panel. Before confirmation, its exact request and hash are written to bounded, workspace/mission-bound sessionStorage (no mission text). Failure to retain or parse that receipt blocks confirmation. After an uncertain response, no new dossier or automatic retry is allowed; Verify receipt uses prepare only. If the server returns the same prepared hash with no reservation, the owner can explicitly retry the same confirmation. Existing reserved/uncertain receipts remain closed. Only recognized pre-effect rejections with their expected HTTP status release the local pending request. Stale dossiers offer an explicit refresh before preparing again.

Reload/navigation restores the pending parameters in the same tab, without automatic HTTP calls. If a server reservation exists but this session no longer has its request parameters, the panel prevents a new confirmation and explains the need for the original session or server reconciliation. A cross-session receipt recovery interface remains future work.

Typecheck/lint/build/smoke are run separately. No real owner-session confirmation, live database write/concurrency or interactive browser enabled-path qualification is claimed by these tests.
