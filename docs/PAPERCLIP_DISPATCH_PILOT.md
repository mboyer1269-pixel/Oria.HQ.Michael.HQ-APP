# Explicit mission handoff boundary

`POST /api/orchestration/missions/dispatch` is disabled unless `ORIA_ENABLE_PAPERCLIP_DISPATCH=1`. No credentials or activation are supplied by this implementation. Owner authentication, authenticated actor attribution and an exact same-origin `Origin` header are required. Body: `{ missionId, expectedUpdatedAt, confirm: true }`; extra properties and query parameters are refused, body capped at 2 KiB with a five-second deadline. Company, workspace, endpoint, token and remote task content are resolved server-side.

This boundary hands off a durable HQ mission as an unassigned Paperclip **backlog** issue. It does not start an agent, claim execution or synchronize remote status back into the mission. The request explicitly authorizes that handoff, not later execution. The mission dossier offers preparation and a separate confirmation only when the server reports a valid enabled binding and missions are persisted in Supabase. Local/mock missions never offer transfer. Only the capability boolean reaches the client; connection configuration remains server-only. Existing receipts show a link or a reconciliation requirement instead of another send button. Network loss and malformed success lock the form for reconciliation; no automatic retry occurs.

The existing Supabase `missions.input` JSONB stores one nested `_paperclipDispatch` receipt. All other input fields are preserved. The production store never falls back to in-memory or seeded missions. Reservation uses one SQL update filtered by mission ID, workspace, status, timestamp and complete original input. That compare-and-swap prevents concurrent dispatch through this boundary. A durable action-ledger entry attributed to the authenticated actor must succeed before the remote request. No second task database or queue is introduced.

The receipt stores `reserved`, `outcome_unknown` or `linked`, company ID, stable correlation key, payload hash, actor, timestamp and eventual remote issue ID. The key derives from company/workspace/mission identity. Paperclip receives this key in the **JSON body** `idempotencyKey`, matching the pinned create schema; an arbitrary HTTP idempotency header is not assumed. `allowDuplicate:true` prevents unrelated title-based deduplication; keyed deduplication remains active. The description contains the same correlation marker for reconciliation. The response must carry the expected company, valid issue UUID and marker before the link is accepted.

Any network, timeout, malformed response or uncertain create result becomes reconciliation-required. There is no automatic resend, even after Paperclip's seven-day key retention. A second call returns an existing link or the reserved/unknown receipt. If the remote issue exists but link persistence fails, the returned ID and stable marker help recovery while the durable reservation prevents replay. A failed completion audit is explicitly reported; the durable mission receipt remains the link of record.

Reconciliation is deliberately not automatic in this slice. An operator must inspect the company issue using the correlation marker, verify identity and payload, and repair the receipt with an audited compare-and-swap; a UI/service for that operation remains required. Do not clear reservations or repeat unknown requests. The existing durable draft writer now uses atomic insert-on-conflict-do-nothing and returns the canonical row instead of replacing an existing mission. It rejects caller-supplied dispatch receipts. Consequently, draft reconfirmation cannot erase a reservation or link. Future writers must preserve this invariant; direct administrative database edits are outside this application guarantee.

The outbound create uses a fixed trusted server origin, no redirects or retries, a five-second deadline and 256 KiB response cap. Upstream errors never expose credentials or response bodies. The existing read-only bridge configuration supplies the company binding; dispatch has its own opt-in flag.
